# AlphaTestbookapp — App Audit & Re-organization Register
**Audit date:** 2026-10-18  
**Scope:** live student app, source/build/release path, question visibility, server sync, data integrity, test/robot reliability, layout and Control Room.  
**Stage:** Phase 1 evidence collection. This is not a claim that every runtime path has been verified.

## Executive verdict
The site and backend are reachable and the latest full automated suite passes, but the app is **not yet audit-clean**. The largest verified risks are release provenance, guest-vs-logged-in question visibility, poor visual interaction/accessibility audit results, and database hygiene. Do not continue bulk importing until these are triaged.

## 2. Confirmed architecture
- Source of truth is `dev/app/src/`; `dev/app/build.py` assembles it using `dev/app/manifest.json`.
- Root `index.html` is the GitHub Pages release output. Do not hand-edit it.
- Question changes should go through `DataCore.commit/mutate`; this preserves integrity checks, backup/snapshot behavior, persistence, indexes, and rollback.
- Supabase RLS intentionally allows students to read active **published** questions only; admins can see all statuses. Draft questions are not supposed to appear in student tests until reviewed/published.
- `cloudPullContent()` fetches question rows through authenticated `Server.select`, relies on RLS, then applies exam/branch filtering via `profileFilterRows`. It paginates in 1,000-row chunks and groups questions into groups of 20.
- Guest view is therefore not the same as the server-backed student view. The current home CTA says Google login is needed to get all questions and sync progress. A guest may only see built-in/local starter content; that is expected by current architecture but should be made unmistakable and verified on a real student session.

## 3. Findings by severity

### P0 — Release provenance is not trustworthy enough
- Root `index.html` starts with `STATUS: UNAPPROVED NEW CANDIDATE; NOT THE OFFICIAL BASELINE` and points to a fixed-host baseline artifact. Source `dev/app/src/html/head-00.html` carries the same marker; `head-01.html` also declares `release-status=PARTIAL-HOLD-RUNTIME-VERIFICATION-PENDING`.
- The live site and source both report V3.4.1, and smoke test passes, but version equality only proves the version string matches. It does not resolve the explicit unapproved-candidate status.
- Required: identify/verify the approved baseline and compare generated output from current source before declaring the release approved. Do not blindly revert to a missing external baseline file.

### P0 — Missing questions can be a login/status visibility issue, not a render bug
- Current architecture requires a valid authenticated session for server sync. Guest mode shows local starter content.
- Students cannot see Draft or inactive rows under the intended RLS policy. The 1,026 Draft rows are intentionally invisible until approved/published.
- Required end-to-end check: on a non-admin student account, verify login/session, published row count, exam profile, branch, topic rendering, test builder, and that Draft/hidden questions remain invisible. Compare app counts with server counts under the same profile.
- Do not publish all Drafts as a workaround.

### P1 — Data hygiene affects discoverability and trust
- 1,581 published questions are untagged/Mixed; users may not find them under expected topics.
- 220 live duplicate questions are flagged. Need report-only inspection and dedupe rules first; do not delete automatically.
- Required: create a reviewable duplicate manifest (IDs, normalized stem/options, answer conflicts, source provenance), then resolve only after backup and answer/source verification.

### P1 — Mobile interaction and readability
- Existing design audit found small tap targets, low contrast, and overlapping controls despite zero overflow/page errors.
- Required: inspect screenshots and prioritize high-traffic routes first: Home → Subjects/Question Bank → Test Builder → Active Test → Result → Revision → Me. Fix shared component/tokens before one-off patches; verify phone 360/412, tablet 768, desktop 1280, light and dark themes.
- Do not optimize only for screenshots; preserve tap targets, focus states, keyboard access, contrast and Hindi rendering.

### P1 — Test and robot reliability
- Latest tests pass, but recent cancellations and failures mean reliability is not green across history.
- PYQ Robot's success rate is lower than other robots. Keep it paused during app audit.
- Required: inspect failed/cancelled run causes and distinguish code defects, runner contention, deliberate cancellation, and workflow-gate pauses. Smoke tests must verify student-visible question rendering and status boundaries, not just HTTP and version.

### P2 — Control Room / Ops task backlog
- 9 of the latest 40 Ops tasks failed.
- Required: classify failure causes and retry only idempotent/retry-safe tasks. Keep approval gates for publishing, restore, and data mutations. Confirm actor/reason audit trail.

## 4. Correct order of work (do not mix changes)
1. **Release baseline:** verify approved baseline → reproducible source build → deployed artifact hash/version → service-worker cache behavior.
2. **Question visibility:** test guest, student, admin separately; verify RLS, sync, profile/exam/branch filter, topic grouping and test builder.
3. **Critical student journey:** Home → Subjects → Question Bank → Test Builder → Active Test → Result → Revision/Mistake Book; check empty/loading/error states.
4. **Admin data workflow:** Draft → review → publish gate; source provenance, bilingual text, four options, answer/solution checks; no auto-publish.
5. **Data cleanup:** report-only duplicate audit, then mixed-topic tagging review; backup and explicit approval before mutations.
6. **Storage/sync/PWA:** IndexedDB hydration and fallback, cross-tab read-only, stale/offline cache, login refresh, multi-page pagination, sync retries.
7. **Design repair:** fix shared controls and overlap/contrast issues based on screenshots; re-run Design Audit.
8. **Reliability:** fix historical CI failures/cancellations and add end-to-end regression checks.
9. **Closeout:** produce a file-by-file pass/fail/blocked table with evidence, change, regression test, and actual result. Only then release.

## 5. Non-negotiable safety constraints
- No bulk PYQ import during this audit.
- No bulk publish, delete, or mass rewrite to make counts appear correct.
- Never edit generated `index.html` directly.
- Preserve DataCore as the sole question-data writer and keep RLS enabled.
- Never treat unit-test success or an HTTP 200 as proof of full app correctness.
- Make isolated changes on separate branches; merge only after required tests and a real live smoke check pass.
